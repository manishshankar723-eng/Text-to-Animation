# Bundled caption fonts

These fifty-six .ttf files are the ONLY fonts an animatic caption can be set in,
and both halves of the app load them from here:

- the **browser** fetches `/fonts/<file>` through the `@font-face` rules
  generated by `client/src/animatic/fonts.js`;
- the **server** opens the same file off disk in `animatic_fonts.py`, which
  `animatic.py` draws the exported MP4 with.

That is the whole point. A font resolved by NAME resolves differently on a
Windows laptop and a Linux server, so the caption you position in the monitor is
not the caption that lands in the video — different width, different wrap,
different number of lines. A file that ships with the project cannot drift.

`tests/captions_check.py` asserts the JS and Python lists are identical, that
every file named in them is here, that each `line_ratio` still matches its file,
and that **each font's declared `scripts` still match its cmap in both
directions** — a face that claims Hindi and cannot draw it fails, and so does
one that quietly gained a writing system nobody declared.

## What each font can draw — and why that is on the list

Every entry carries a `scripts` list, and none of it was typed by hand.
`tools/fonts_sync.py` reads it out of the file's own character map, checks the
glyphs are not empty stubs, and prints the entry to paste into both lists.

The reason it exists: **every font in the picker draws something.** Set a Hindi
title in Anton and nothing warns you — the panel looks fine, the render runs,
and the customer gets ▯▯▯ in a video they paid for. So the coverage is measured,
the editor warns before the export instead of after, and captions the app
generates on its own (subtitles, anything the chat agent writes, an imported
Premiere timeline) resolve their own font through `best_font_for_text`.

们. Pick from the shelf named for your language and this never comes up; pick a
Traditional face for Simplified text by hand and the coverage warning will not
catch it. Fixing that properly would mean shipping every face's character map to
the browser, which costs more than it saves.

## Complex scripts need more than a font

Thirteen of the writing systems above reorder, join or stack their characters:
`हिन्दी` is six characters and four glyphs, in a different order. Turning one
into the other is called shaping, and the exporter needs **FriBiDi** present to
do it — read `text_shaping.py` and `vendor/fribidi/README.md`. Without it those
captions export malformed while the preview looks correct, so
`tests/captions_check.py` fails outright and `build_animatic` refuses to render
a project that contains one.

Where a family only ships as a VARIABLE font upstream, the file here was frozen
to a single static weight by `tools/fonts_sync.py` — never shipped variable. A
variable font would let the browser pick an instance through CSS `font-weight`
and Pillow pick one through `set_variation_by_name`, which is two mechanisms
agreeing by luck; one static weight per entry is the same rule as "one weight
per family" below.

## Adding one

Add an entry to `WANTED` in `tools/fonts_sync.py`, then:

```bash
pip install -r requirements-dev.txt        # needs fonttools
python tools/fonts_sync.py --write --only <group>
```

It downloads the file from `github.com/google/fonts`, freezes it to the weight
you asked for if upstream only ships variable, measures `line_ratio`, reads
`scripts` off the cmap and prints the entry. Paste that entry into **both**
`animatic_fonts.py` and `client/src/animatic/fonts.js`, add the copyright line
above, and run `python tests/captions_check.py`. Nothing else: the picker, the
`@font-face` rules and the exporter are all generated from those two lists.

⚠ **Do not re-fetch the fourteen original faces.** Every animatic exported so
far was drawn with those exact files. A fresh cut from upstream has different
metrics and would re-wrap captions in projects nobody has opened.
`tools/fonts_sync.py` keeps them in a separate `ORIGINAL_FOURTEEN` table that is
measured and never downloaded.

⚠ **Pick ONE weight per family and name the file for it.** There is no bold or
italic axis on a caption — a face is a whole entry on the list. If a project
wants Inter Bold, that is a second entry (`inter-bold`) and a second file, not a
flag.

⚠ **A new writing system needs a `SCRIPTS` row too**, in both lists, with the
Unicode ranges that identify it and whether it needs shaping. Without one the
font's coverage cannot be required by any caption, and `captions_check.py` fails
with "no font sits on a shelf no caption can reach".
